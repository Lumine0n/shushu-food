# 美食清单建设方法

推荐好不好用，九成取决于清单。这份文档讲清单从哪来、怎么记、记到什么程度算够。

## 1. 以“具体的菜”为单位，不以店为单位

用户想知道的是“今天吃什么”，不是“去哪家店”。所以 `data/foods.json` 里每一条都是一道菜：

- 同一家店的几道好菜，分成几条记（比如泰煌鸡的白斩鸡、鸡汤面各一条）。
- 不推荐的菜**不进清单**，可以写进同店其他菜的 `reason` 里当小贴士（比如“这家不推荐意大利面”）。

## 2. 多个来源，统一审核

| 来源 | 怎么做 | `source` 填什么 |
|---|---|---|
| 自己实地吃过 | 吃完当天记下来最准 | `用户实地整理` |
| 朋友推荐 | 问清楚菜名、店名、大概价钱 | `朋友推荐` |
| 狐友“上海大学圈” | 用 `scraper/` 脚本抓帖子，进待审核清单，人工确认 | `狐友上海大学圈`，`sourceUrl` 填帖子链接 |
| 大众点评 / 小红书 | **只记结论**（菜名、价位、好在哪），不搬原文和图片 | `大众点评摘录` 等，`sourceUrl` 填链接 |
| 网页上的“推荐一道菜” | 收到的 GitHub Issue 同样走审核 | `网友推荐` |

不管哪个来源，都要先确认“这道菜现在还在卖、店还开着”，再加进来。

## 3. 统一字段和词表

问题和数据必须一一对应，网页才能筛选。所以下面这几个字段**只能用固定的词**：

| 字段 | 可选值 | 怎么判断 |
|---|---|---|
| `protein` 主料 | 牛肉、鸡肉、猪肉、鱼虾、素食、其他 | 这道菜最主要的肉；没肉算素食；拿不准或混合的算其他 |
| `staple` 主食 | 米饭、面、粉、汉堡披萨、其他 | 吃完能不能饱、靠什么饱；火锅、凉菜、小吃算其他 |
| `flavor` 口味 | 辣、不辣、清淡 | 清淡比不辣更进一步（选“不辣”时清淡的菜也会出现） |
| `price` 人均 | 数字（元） | 一个人吃这道菜大概花多少；网页会自动分到 20 以内 / 20–40 / 40 以上 |
| `scene` 场景 | 一个人、聚餐、带走（可多选） | 份量和吃法 |

想加新的选项（比如主食加“饺子”），要**同时**改 `questions.js` 和清单里对应的菜。

## 4. 用 `mentions` 记录口碑

同一道菜被不同的人、不同的帖子提到，不要重复加一条，而是把 `mentions` 加 1。`mentions` 越大，摇到它的机会越大。

判断“同一道菜”：**店名 + 菜名**相同（允许“肉夹馍”和“肉夹馍（五花/纯瘦）”这种小差别，人工合并）。

## 5. 每条都能追溯

- `source`、`sourceUrl` 一定要填，方便以后核对。
- `addedAt` 填加入日期。
- 定期（比如每学期开学）过一遍：关店的删掉；涨价的改 `price`；口碑变差的在 `reason` 里注明或删掉。

## 6. 先做“覆盖”，再做“数量”

现在清单只有 18 道菜，很多组合会触发“放宽条件”。建议目标：

1. **先凑够约 50 道菜。**
2. **每道题的每个选项至少有 3 道菜。** 目前明显缺的：
   - 主食“粉”：0 道（螺蛳粉、米线、酸辣粉都可以补）
   - 主料“鱼虾”：1 道
   - 预算“20 元以内”：只有几道（食堂、小吃档口是好来源）
   - 口味“辣”：基本都是火锅，缺一个人能吃的辣菜（麻辣烫、川菜盖饭）
3. 再追求数量和多样性。

可以在项目根目录用下面这行命令快速数一数每个选项有几道菜（需要 Node.js）：

```bash
node -e "const f=require('./data/foods.json');for(const k of ['protein','staple','flavor']){const c={};f.forEach(x=>c[x[k]]=(c[x[k]]||0)+1);console.log(k,c)}"
```

## 7. 收集渠道

- 网页结果卡片底部有“知道一道好吃的？推荐给我们”，会打开一个 GitHub Issue 模板。
- 收到的推荐和抓取来的候选一样，**人工确认后**再并入 `data/foods.json`。
